# winkox

winkox is a Next.js gaming and earning platform with a player lobby, original games, wallet flows, referrals, notifications, support chat, and a role-based admin panel.

## Requirements

- Node.js 20 or newer
- npm
- MySQL 8+ or a compatible MySQL/MariaDB server for server-side data

## Install and run

```bash
npm install
npm run dev
```

Open `http://localhost:3000`.

Other commands:

```bash
npm run typecheck
npm run lint
npm run build
npm run start
```

## Agent device security

The top-level **Agent** is database role `owner`, not the referral-player `agent` role. Only this top-level account can open **Login devices**, search accounts, and view active distinct browser/device counts and login details for players and staff. Revoked or seven-day-expired sessions and inactive accounts are excluded; repeated logins in a remembered browser count once. Legacy sessions without browser identifiers count separately.

Successful Super Admin (`admin`) logins from a previously unseen browser create an Agent-only warning linked to the device page, delivered through the notification bell/popup and live notification sound. MySQL commits the session and warning together, serializing per account to avoid duplicate warnings. A signed, HttpOnly first-party `wx_device` cookie remembers the browser for one year; changing IP or logging out/in does not itself mean a new device. Clearing cookies, private browsing, or using another browser does. This identifies browser installations, not physical hardware.

Agent-origin block/unblock, wallet changes and transaction approval/rejection produce no player/admin notifications, including first-deposit bonus and referral-commission notices. Accounting, bonuses, commissions and audit records remain intact. Agent broadcast sending is explicitly disabled rather than reporting an unsent message as successful. Other staff and automatic system notifications are unchanged.

## Player quick-bet amounts

Players can open **Customize bet amounts** in their profile and save five distinct quick-bet values (10–50,000). New accounts start with Rs. 10, 20, 50, 100 and 200. Values are stored on the player account and used by the shared preset array consumed by game bet controls. Previously saved amounts below Rs. 10 fall back to these defaults. `npm run test:bet-presets` checks defaults, validation and per-player isolation.

## Player wallet controls

Player-facing games do not offer demo-balance resets, free-credit refills, arbitrary top-ups or balance-reset bonuses. Round restarts, bet selection, statistics-only resets and wallet viewing do not modify funds. Accepted wagers, confirmed winnings/cashouts, valid cancellations/refunds and existing deposit/withdrawal flows retain their original accounting; initial wallet fallbacks are unchanged.

Run `node --test scripts/test-player-wallet-controls.mjs scripts/test-card-wallet-controls.mjs scripts/test-slot-wallet-controls.mjs` for control-removal and preserved-accounting regressions.

## Disclosed 35% daily prize pools

Catalog games use the same disclosed contract, with a **separate daily pool per game**, not one shared balance between games. This is a **different payout contract**, not a change to outcome probabilities: 35% of accepted, non-refunded stakes is the target pool, **including returned stake and profit**; the remaining 65% is retained by the platform. A successful result or cashout locks a provisional gross-return claim (including returned stake and game bonuses), without immediate wallet credit. After the Pakistan UTC+5 day ends and **all** its wagers finish, cryptographically sampled positive weights randomly divide the pool between successful wagers. Zero claims receive no allocation when successful claims exist. If no wager has a positive claim, all accepted stakes are used as weights, including no-win rounds. A sole bettor receives 35% of their eligible stake. Integer largest-remainder allocation and chronological fractional-paisa carry preserve the total budget. Unfinished interactive wagers can delay settlement indefinitely; later days wait for earlier unresolved days.

All game entries mount their native engine directly without the shared pre-game rules, ratio, pool-ledger or consent popup. The shared wrapper still reports game-status and wallet synchronization errors and blocks unsupported wager integrations explicitly. Removing that presentation does not grant consent, activate a pool, alter server accounting or change payment methods. Existing server-side rules-version checks for pool-enabled wagers remain enforced. Teen Patti Royal chips select the displayed stake, which is charged once without an additional boot fee; folding produces a zero claim.

Whole paisa uses deterministic largest-remainder allocation; fractional paisa carries forward per game. Refunds leave the pool. New-mode payouts have no additional house-share/WinHold deduction. Existing accepted legacy wagers retain their old payout and wallet behavior. Pending claims are labelled in-game and in player records; paid amounts appear only after transactional settlement. Pool rules and an explicit acknowledgement are required before new-mode bets; the server checks the rules version.

**Deployment / activation:** the feature is **on by default when MySQL is configured**. Without MySQL, the app retains legacy local-wallet mode rather than requiring a transactional store. Every Node.js server instance starts an in-process scheduler (`src/instrumentation.ts` -> `src/lib/dailyPoolScheduler.ts`) that settles all game pools every minute whenever MySQL is configured, so no external cron is required. Set `DAILY_POOL_ENABLED=false` only to fall back to legacy per-round payouts for new bets. The optional `/api/cron/daily-pools` endpoint remains available for an external scheduler when `DAILY_POOL_CRON_SECRET` is set; do not put the secret in a `NEXT_PUBLIC_` variable.

The scheduler advances abandoned flight reservations (including Aviator X's personal rooms), the twelve multiplayer tables and Dragon Tiger/Andar Bahar, then settles eligible pools. It does not force unfinished interactive wagers to lose. It is safe to retry after errors or downtime: room locks, wallet row locks, immutable wager IDs and settlement state prevent duplicate credit. One failing game does not prevent processing later games; failures are logged and retried on the next tick (the optional cron endpoint returns HTTP 503 with the failed game slugs). Authenticated status reads and game actions also attempt settlement. Monitor scheduler failures; a missing wallet/result or ledger mismatch rolls the transaction back with an explicit server error and requires operator review.

`/api/player/daily-pool?game=<slug>` exposes only the signed-in player's latest 30 pool entries and actual wallet balance. Account reset/deletion is blocked while that account has unresolved pool wagers. History cleanup retains pending pool results/source records; pool audit ledgers are not part of ordinary history cleanup. Disabling new pool bets does not cancel existing pool obligations: keep the scheduler secret and schedule until all accepted wagers settle.

Browser games must use an explicit accepted-wager lifecycle rather than arbitrary wallet deltas. The old balance-delta endpoint rejects new-mode payouts. Unsupported integrations are blocked explicitly instead of silently retaining legacy payouts; check the [browser coverage notes](docs/daily-pool-browser-coverage.md) before activation. Drain legacy browser sessions before enabling the new contract; do not switch an already debited legacy round to a new-pool claim.

Run `npm run test:daily-pool` for mock-transaction accounting, all twelve multiplayer integrations, dedicated game/browser lifecycle checks, UTC+5 boundaries, carry, fallback allocation, >1,000 entries, claim/refund idempotency, rollback and legacy compatibility. No real-money wagers are made by these tests.

### Card-game selection and Plinko prize cycles

New wagers in the 26 card titles enumerated in `src/lib/cardGameRules.ts` (including Football Studio) use **instant wallet accounting**, independently of `DAILY_POOL_ENABLED`. Accepted stakes are debited by the server, and confirmed round winnings are credited transactionally; browser balance changes are not a substitute for server confirmation. `/api/player/daily-pool` reports pool mode disabled for these new card wagers while continuing to expose older pool entries. Existing accepted `poolVersion` wagers remain governed by their original deferred settlement contract and must not be paid twice or retroactively converted. Run `node --test scripts/test-card-wallet-policy.mjs` for policy/API coverage.

Server-cycle migration covers all 20 browser card titles in `SERVER_BROWSER_CARD_GAMES`: Poker, Poker Betting, Muflis, Best of Four, AK47, Red vs Black, Three Cards, Amar Akbar Anthony, Bollywood Casino, Faceoff, Hukam, Joker, Blackjack, Monster Hi-Lo, Rummy, Teen Patti, Teen Patti 999, Texas Hold'em, Three Card Poker and Casino War. Each completed cycle assigns 30 winning slots to 100 player-rounds, including repeat players. Multiple chips, extra stakes and retries within one round do not draw another slot. Rummy retains 30 fully meldable hands per 100 deals. Interactive folds, surrender or continued guesses can forfeit an opportunity, so arbitrary play can finish with fewer than 30 profitable wins. New `bet-wins-30-of-100:v1` cycles start fresh (Rummy retains its existing bet cycle); historical player-cycle documents and already assigned outcomes are preserved.

New Dragon Tiger, Andar Bahar, Baccarat, Speed Baccarat, Football Studio and 32 Cards wagers use player-specific rounds, not a common public result. Their server cycles assign 30 winning opportunities per 100 player-rounds, including repeat players. The existing 2x gross-return caps remain on Dragon Tiger, Andar Bahar, Baccarat, Speed Baccarat and 32 Cards; Football Studio and Dream Catcher preserve their existing paytables and house-share split. Old already-accepted shared wagers retain their original cards, paytable and accounting contract; they must finish before that player switches to the personal table. Guest spectator rounds never reveal another player's private cards or wagers.

For 32 Cards, the 30 winning opportunities comprise 24 EVEN and six ODD results, preserving the earlier 80/20 parity split and referring to the **final total of the winning hand**, not Player 8/9/10/11's base number. A main-player spot can win with either parity; an EVEN/ODD side spot can win only with its matching parity. If only incompatible winning slots remain, the server refuses that side bet before debiting funds; a compatible spot is needed to finish the cycle. This quota cannot make 100 EVEN-only bettors include six genuine ODD-bet winners.

Baccarat, Speed Baccarat, Football Studio, Dream Catcher and 32 Cards lock the first selected spot for that personal round; repeated chips on the same spot remain supported. Covering multiple outcomes is rejected explicitly. Cancelled stakes are refunded once, but cancellation does not redraw the assigned slot; cancelled winning opportunities can leave fewer than 30 paid wins. On capped titles the existing 2% hold is included in, not added above, the 2x gross cap. The pre-migration shared-room regression fixture remains separate from the real private-table integration tests in `scripts/test-private-card-tables.mjs`.

Allocation-based browser tables require a selection that can produce both a genuine profitable win and a zero-return result. Fully covering every outcome or side-bet combinations that cannot satisfy both are explicitly rejected before consuming a cycle slot; players can undo or clear those bets. Existing bet controls remain visible. Interactive tables keep accepted wagers open between moves, validate every action under the game transaction lock, and restore their saved public state after reload. Client-supplied payouts and post-deal refund, stake-reduction or arbitrary extra-stake requests are rejected; only validated table moves can settle the wager or add a stake.

Previously accepted pooled card wagers other than Poker retain their `TEN_WIN_POOL_GAMES` settlement rules. That selection targets 10 winning wagers per 100 accepted wagers, choosing from positive provisional claims when available. It can pay fewer if there are fewer eligible claims. It is not a ten-distinct-player outcome guarantee. Per-wager targets remain 1x-2x, subject to the available daily budget. New instant-accounting card wagers do not enter that settlement lottery. Native card layouts and dealing animations are unchanged.

Poker uses a server-authoritative game-wide cycle instead of the former browser-side 35% random roll. Each completed cycle of 100 player-rounds contains exactly 30 winning slots and 70 losing slots, including repeat players. Winner selection, the matching card deal, confirmed payout and consumed slot commit together under the per-game transaction lock. Duplicate requests return the same deal, and failed transactions do not consume slots. Existing hand paytables and reveal timing remain unchanged. Previously accepted wagers keep their saved original result.

Birds & Beasts uses a game-wide server cycle of 100 player-rounds. A player's round counts once regardless of how many options or chips were staked; authenticated idle rounds also count once. All bet combinations remain accepted. Each completed cycle has exactly two x8 landings combined (Owl and Panda), two x12 landings combined (Eagle and Lion), one Golden Shark and one Silver Shark. Both Sharks land during rounds 91–100; appearance counts apply whether or not a player bet on the result. The remaining 94 landings use x4/x6 animals. The server securely shuffles the appearance schedule and 20 winning/80 losing target flags before the cycle, then chooses a matching light within the scheduled category when possible. A winning round means its total payout exceeds its combined stake. Actual wins can differ from 20 because player selections or forced appearance quotas can make a target result impossible; impossible targets do not skip a counted round, falsify the result, or change the paytable. A 20% winning-round target is not a 20% RTP guarantee. The new `rounds-20-target:v2` cycle starts fresh on first use; earlier 30-of-100 bet-cycle records and completed results are preserved but do not determine the new cycle. The screen's locally retained round number is not the game-wide server cycle position. Paid results, cycle progress and wallet settlement commit together; paid replays return their existing result. The idle `/api/spin` endpoint requires authentication and a stable `roundId`, deduplicates retries under the same game lock, and never settles paid bets or updates wallets. Wallet credit is recorded atomically at confirmation, with the displayed balance held until the wheel reveals the result. Game design, multipliers and payouts are unchanged.
Previously accepted Poker pool obligations still use `EXACT_CLAIM_POOL_GAMES`: daily settlement allocates their available pool against server-generated claims without a second winner-selection lottery. That old pool budget can still reduce individual payments; new instant wagers do not enter it. Run `node --test scripts/test-poker-player-outcomes.mjs scripts/test-browser-recovery.mjs` for complete 100-player cycles, matching card scores, wallet settlement, concurrency, retries, rollback, repeat-player restrictions and reload recovery.

Run `node --test scripts/test-browser-card-outcomes.mjs scripts/test-card-remaining-deals.mjs scripts/test-interactive-cards.mjs scripts/test-card-wallet-policy.mjs scripts/test-browser-recovery.mjs` for the browser-card migration, validated interactive moves, covered-allocation rejection, wallet bypass prevention and accepted-wager recovery.

### Roulette player cycles

All five local roulette titles (European Roulette, Auto Roulette, Lightning Roulette, Mini Roulette and Poker Roulette) generate personal server-authoritative results with 30 winning slots and 70 losing slots per completed cycle of 100 player-rounds, including repeat players. Secure sampling without replacement randomizes slot positions. New bet cycles start fresh; historical player cycles and already generated results are retained. A round's **combined gross return is capped at 2x its total accepted stake**, including returned stake and any hold. Winning spots and revealed numbers/cards agree with confirmed payouts. Compatible multi-spot allocations remain supported; covering all outcomes is refused. Spectator spins and fully cancelled live roulette wagers consume no slots. This win quota is not an RTP guarantee.

The three additional local wheel games are Dream Catcher, Hotline and Wheel Betting: 34 local games total when combined with the 26 card games and five roulette games. These wheels also assign 30 winning slots per 100 paid player-rounds and settle new wagers instantly, bypassing the old ten-win daily-pool lottery. Dream Catcher uses a personal, fixed numbered spot per round; multiplier-only spots are rejected. Wheel Betting selects a segment from the assigned win/loss group using a random hash; that hash does not prove independent win probability. Provider-hosted Evolution and other external catalog titles are not local engines and their outcomes cannot be configured here.

New roulette wagers use instant accounting regardless of `DAILY_POOL_ENABLED`: acceptance debits the stake, and verified settlement credits the winnings once. Arbitrary roulette balance deltas and unverified new client terminal claims are rejected. Existing accepted shared/pool wagers retain their original cards/wheel, paytable and deferred contract. Auto and Lightning Roulette finish old shared obligations before opening the player's personal table; guests cannot see another player's personal number, bets or history. Personal live rounds select a slot only after betting closes, and fully cancelled rounds consume none. Duplicate requests and database rollback cannot debit, credit or consume a slot twice.

Run `node --test scripts/test-browser-roulette-outcomes.mjs scripts/test-private-roulettes.mjs scripts/test-multiplayer-wheels.mjs scripts/test-card-wallet-policy.mjs scripts/test-browser-recovery.mjs` for all five roulette 100-player cycles, wheel/payout agreement, multi-spot caps, privacy, cancellation, queued bets, rollback, repeat-player restrictions, immutable recovery and old shared/pool-wager compatibility.

### Slot player cycles and payout limits

Lucky 777, Treasure Bowl, Fortune Ox, Fortune Gems, Fortune Toucan, Gates of Olympus and Diao Chan now join Super Fruits and Sweet Bonanza in using server-authoritative results: ten positive-return opportunities per completed cycle of 100 distinct admitted players, per game. Repeat players cannot draw another winning slot within an unfinished cycle. Results, consumed slots and verified wallet settlement commit transactionally; rejected bets, retries and rolled-back transactions cannot create extra wins.

Hotline uses a separate game-wide cycle with exactly 30 winning bets and 70 losing bets per completed block of 100 resolved wagers. Each new wager counts, including repeat players; cryptographically secure sampling without replacement puts wins at random positions, not a fixed sequence. The selected colour matches the server result on a win, with existing payouts and the 2x gross cap unchanged. Cycle consumption and wallet settlement are atomic; retries reuse the recorded outcome. The new 30-bet cycle starts fresh without deleting historical ten-player cycles or settled wagers. This is a bet-win count, not an RTP guarantee. Losses no longer display “No win” in the result or history.

Fishing Arcade, Derby Race and Rummy each use their own cryptographically random 30-of-100 wager-opportunity cycle; repeat players count on every new wager. Fishing consumes a slot atomically at shot acceptance and returns the assigned flag on acceptance/replay. Shots without an opportunity cannot submit a positive terminal claim; existing target/collision behavior is retained, so a missed or unfinished winning shot can forfeit it. Rummy consumes a slot on the first deal: 30 fully meldable hands per 100 dealt wagers; valid declarations pay the existing 2x, while forfeits still pay zero. Thus neither game guarantees 30 paid wins per 100 completed wagers. Derby consumes a slot when resolving the accepted horse selection, produces a matching authoritative race plan and settles once with the existing 2.75x payout; the displayed wallet credit is held until the finish. Unbet spectator races do not consume slots. Replays and transaction rollbacks do not create additional opportunities. New 30-wager cycles start fresh; historical results and previously accepted legacy wagers remain intact. Other games retain their existing win policies. These are win-opportunity counts, not RTP guarantees or independent fairness certification.

New slot wagers debit on acceptance and credit confirmed returns directly, regardless of `DAILY_POOL_ENABLED`. Each paid wager's **combined gross return, including bonus/free spins, returned stake and any hold, is at most 2x the stake**: Rs.100,000 cannot create a new Rs.400,000 return. Base paytable values do not override the paid-wager cap. Super Fruits keeps its five cherry, three lemon and two orange allocation; Sweet Bonanza keeps its 1.2x/1.4x/1.6x returns. A positive return at or below 1x is not profit. Old accepted client-terminal and pool wagers retain their original completion and deferred settlement contracts; deposits and withdrawals are unchanged.

## Database setup

The application creates its JSON-backed tables on first server connection. To test the configured MySQL connection and ensure the tables manually, run:

```bash
node scripts/test-mysql.mjs
```

The script requires the same `MYSQL_*` variables as the application and does not create a database; create the database and user first.

Financial transactions replace a failed connection at most once while checking the connection, setting isolation, or starting the transaction, before acquiring the game lock or running any wallet work. Connection failures after that point, including a lost commit response, are surfaced without replay to avoid duplicate payouts. Run `node --test scripts/test-multiplayer-store.mjs` for these boundaries; persistent connection resets still require a reachable database.

Live chat uses the `supportthreads` and `supportmessages` JSON-document tables. The application creates them on startup; to create them manually, run [scripts/live-chat-schema.sql](scripts/live-chat-schema.sql) against the selected database. Users must sign in again after deploying the authenticated chat update so the server can issue a secure session cookie.

The schema reference for Hostinger deployments is in [scripts/hostinger-schema.sql](scripts/hostinger-schema.sql). The runtime model abstraction is in [src/lib/db-model.ts](src/lib/db-model.ts), with MySQL connection handling in [src/lib/mysql.ts](src/lib/mysql.ts).

## Gregmorn provider games

The website currently displays the saved local games in the lobby, player catalogue,
admin game controls, user restrictions and per-game results. `LOCAL_GAMES_CONNECTED`
is enabled and `PROVIDER_GAMES_VISIBLE` is disabled in `src/lib/gameAvailability.ts`.
Local games use their existing `GAME_IMAGES` artwork and game routes; saved ON/OFF,
Hot settings, restrictions and history remain in place. The local browser catalogue
has a separate cache so previously cached API games cannot appear after the switch.
Gregmorn credentials, integration endpoints, wallet callbacks and provider records are
retained for later use; panels do not fetch the provider catalogue in this mode.

The public artwork registry includes the supplied images for all 158 games in the latest catalogue audit. `Hi-Lo` and `Hilo` retain separate exact-title mappings because punctuation normalization would otherwise conflate their two supplied images. Regenerate the artwork reports when games or image files change.

The Gregmorn seamless-wallet integration defaults to the Stage hosts from the OpenAPI specification (`https://office-api-dev.helcenac.com` for login/catalogue and `https://client-api-dev.helcenac.com` for game launch). After Stage acceptance, configure `GREGMORN_OFFICE_API_URL=https://office-api.gregmorn.org` and `GREGMORN_CLIENT_API_URL=https://client-api.gregmorn.org` for Production. Configure `GREGMORN_API_LOGIN`, `GREGMORN_API_PASSWORD`, and `GREGMORN_HMAC_SECRET` as server-only environment variables; never expose them as `NEXT_PUBLIC_*`, commit credentials, or use the sample credentials in the OpenAPI document. Set `GREGMORN_CURRENCY`, `GREGMORN_LANGUAGE`, `GREGMORN_EXIT_URL`, and register the HTTPS `GREGMORN_CALLBACK_URL` per currency in the Gregmorn BackOffice. The callback endpoint is `/api/gregmorn/wallet`.

The platform wallet remains PKR. Default player/admin catalogues merge PKR and USD catalogues by exact provider game ID, preferring enabled PKR entries and using enabled USD entries only when PKR is missing or unavailable. Explicit catalogue `?currency=PKR` or `?currency=USD` requests remain currency-specific. Launch currency is selected server-side from this merged catalogue, never from a browser-supplied currency. Both currencies use nominal 1:1 wallet units: a 10-unit stake debits Rs10, a 15-unit payout credits Rs15, and launch/balance numbers are unchanged. There is no FX rate or separate USD wallet. Provider requests/responses retain their real PKR/USD labels; this local policy does not change Gregmorn's merchant billing or settlement obligations and does not bypass provider personal/table limits. Register callbacks for both currencies and verify their availability with the provider before live play.

When a game's currency differs from `GREGMORN_CURRENCY` (default PKR), its provider login is prefixed with `usd.` or `pkr.`. This lets signed pre-session balance reads resolve the same display ID and return the correct provider currency even when no session or currency field is supplied. Existing unprefixed logins retain their configured-currency behavior. Signed callbacks with a currency must match their registered session (or currency-prefixed balance login); mismatches are rejected, not converted. History amounts remain local PKR units and new result metadata records the provider currency and nominal-unit policy.

The catalogue lists all valid API entries, including entries with `isEnabled: false` or omitted availability. Omitted `isEnabled` does not mean OFF: games returned without this flag are enabled by default and follow the admin's saved ON/OFF and Hot choices. Explicit provider `false` remains unavailable and cannot launch. Admin-hidden games and player restrictions remain excluded; OFF games never appear in player Hot Games. Settings are re-read on every catalogue request, including warm provider-cache requests. Player panels do not display game counts; All Games retains Load More without a remaining count and the lobby appends cards while sliding. Artwork reports include both playable and unavailable games and record their provider availability status.

Launch errors display a safe support code identifying the failing stage or provider rejection class (for example `signature_rejected`, `wallet_callback_rejected`, or `session_registration`). If Gregmorn explicitly rejects a real-money launch because a previous round/session is still active, the launch endpoint returns HTTP 409 with `code: "session_in_progress"` and `Retry-After: 10`. The panel shows a waiting status and retries the real-money launch every 10 seconds until it succeeds or the user selects Cancel or leaves the panel. Every retry rechecks the active account, current balance and game restrictions. Games never switch automatically into demo mode, including providers without demo support. Other provider errors stop the wait and display the launch error; vendor outages and broken provider URLs are not session-wait conditions. Cancelling stops browser retries/navigation but cannot undo a session already being created at the provider. Server logs include the stage. Raw provider rejection messages, request signatures and game-session URLs are not returned in error responses. A successful launch does not prove that signed wallet callbacks can reach the deployed HTTPS endpoint.

Gregmorn may send signed `getBalance` during `openGame`, before creating a session ID. Every balance read validates the `login` passed as `player_login` during launch, resolving `player_display_ids.random_id` to `user_id` on the transaction's MySQL connection and reading the active client wallet. It never queries provider sessions, even when a session ID is supplied, and uses a login-scoped callback lock. A missing, null or empty `sessionid` is allowed only for this balance read. Display IDs are not stored in user JSON; they are the permanent random IDs assigned by `getPlayerDisplayId`, not the mapping table's sequential `display_id`. The actual wallet balance is returned, releasing legacy game holds through the existing atomic path. No session is created or guessed. Unknown/inactive/ambiguous players are rejected. All bet, payout and rollback callbacks continue to require the registered session returned by `openGame` and a matching login. HMAC verification is required before every lookup. Rejected callback identity/session/player mappings log only command and boolean validation flags, never player logins or session identifiers.

For provider messages such as "Shared balance error" or "Bet failed unknown error", inspect the deployed Node app logs at the failure time. Every rejected wallet HTTP callback emits `[gregmorn wallet callback] Rejected` with only `reason` and `httpStatus`, including malformed requests, invalid signatures, unknown sessions, invalid amounts and insufficient funds. This diagnostic does not log request bodies, player identities, transaction/session IDs, signatures or balances, and does not relax validation or change settlement. Callback error responses use `Cache-Control: no-store`. Deploy this change before reproducing; logs from the local app do not show callbacks sent to the live HTTPS callback URL.

Transaction validation errors identify invalid field names and their expected format without echoing their values. These responses include the confirmed current wallet balance rather than a default zero. The callback also accepts the confirmed Evolution bet format (`type: "bet"`, `action: "bet"`, `amount`, `currency`, `round_id`, `game_uuid`, `player_id`, `session_id`, `transaction_id`) after verifying the exact raw-body signature. It maps this to a debit-only `writeBet`. The vendor's `game_uuid` is not the Gregmorn catalogue `gameId`: it is retained as `vendorGameUuid` in history and replay fingerprints, not compared to the launch catalogue ID. The registered session and matching player login determine wallet ownership, reporting game and restrictions; currency must still match. Existing `cmd` callbacks, payouts and rollbacks keep their strict catalogue `gameId` checks and cannot supply a vendor UUID to bypass them. Other vendor action formats are not inferred: obtain the exact signed wallet callback before adding them. Deploy the updated callback endpoint and verify a Stage bet/retry/payout cycle before real-money use.

For temporary deployed-session diagnostics, set server-only `GREGMORN_WALLET_DEBUG=1` and restart the Node application. Signed mutation callbacks emit `[gregmorn wallet debug] Session validation` with command/format, boolean checks and truncated SHA-256 references for correlation. No raw payloads, player IDs, balances, session/transaction IDs, credentials or signatures are logged. This does not bypass validation, enable framework-wide debug mode or prove a transaction committed; check the callback response and rejection/error logs as well. Set it back to `0` and restart after diagnosis. Local environment changes do not enable logging on the deployed server.

The player receives a success notification and the existing congratulations popup (checked while the page is visible); wallet balance is refreshed when the popup arrives.

## Aviator and Aviator X: capped crash model

New commitments use `aviator-80-pre2-v2`: approximately **60% of rounds crash strictly below 2.00x**, across random multipliers from 1.00x through 1.99x. This is a long-run probability, not a forced quota in each set of rounds. Existing `aviator-80-capped-v1` commitments and accepted wagers retain their original rules. Both models replace the former crash bands, winner-triggered crashes, extra win holds and deferred daily-pool allocation **only for these two games**. Crash results never depend on wallets, wagers, previous outcomes or the number of cashouts. The maximum generated crash is **99.99x**, with permitted cashouts **1.01x through 99.98x**, in hundredths. A crash at the selected cashout multiplier loses; 99.99x and 100x cashouts are unavailable. A 1.00x crash loses immediately.

### Distribution and theoretical return

For each round a fresh 256-bit server seed comes from Node `randomBytes`. Take the first 52 bits of HMAC-SHA256 of `<published-model>:<table>:winkox-aviator-public-v1:<roundNo>`, keyed by the UTF-8 hexadecimal server seed. With `D = 2^52` and `N = sample + 1`, generate integer crash hundredths `B = min(9999, max(100, ceil(80D/N)))`. The original v1 result is `C = B`. For v2, `C = 199` when `B = 200`, otherwise `C = B`. Moving only the former 2.00x probability mass onto 1.99x makes strictly-below-2x probability 60%, to within one 52-bit sample, without changing any other cashout target's reach probability. New v2 rounds therefore never crash exactly at 2.00x. Both games use the same distribution, with their existing different flight speeds and panel counts.

Under the cryptographic uniform-output assumption, for every permitted target `t = k/100`, `101 <= k <= 9998`, strict success is `C > k`. Set `q = 200` for v2's `k = 199`, otherwise `q = k`; then `P(success) = (ceil(80D/q)-1)/D`. V2's theoretical RTP is approximately **79.6% at 1.99x** and **80% at all other supported fixed targets**, before payout rounding. V1 remains approximately 80% at every supported fixed target. The discrete-sample error in RTP is smaller than `99.98/D`. In v2, `P(C < 200) = 1 - (ceil(80D/200)-1)/D`, approximately 60%; the original v1 strictly-below probability was approximately 59.799%. Folding the upper tail onto 99.99x preserves supported survival probabilities because all targets are strictly smaller than the cap. There is about 20% probability mass at 1.00x and about 0.80016% at 99.99x. Cashing out at the cap would instead return zero, so that target is rejected.

| Target | Approximate reach probability | Gross theoretical RTP before paisa rounding |
|---|---:|---:|
| 1.20x | 66.6667% | 80% |
| 1.50x | 53.3333% | 80% |
| 1.99x (v2) | 40.0000% | 79.6% |
| 2.00x | 40.0000% | 80% |
| 3.00x | 26.6667% | 80% |
| 5.00x | 16.0000% | 80% |
| 10.00x | 8.0000% | 80% |
| 20.00x | 4.0000% | 80% |
| 50.00x | 1.6000% | 80% |
| 99.98x | 0.80016% | 80% |

This is a nominal 80% theoretical gross return / 20% house edge, with the explicit v2 1.99x exception (79.6% return / 20.4% edge), not a guaranteed session result or a claim that every multiplier returns exactly 80%. Payouts truncate fractional paisa: for stake `b` paisa and target `k/100`, expected payout RTP is `floor(b*k/100)/b * P(success)`. Thus small stakes can return slightly less than the target's unrounded RTP; manual request/network latency also affects achievable results. Crash points are not manipulated to force observed RTP.

For example, Rs.10 at 1.01x pays Rs.10.10 on success and has approximately 80% theoretical RTP. Rs.10.01 at 1.01x pays Rs.10.11 and has approximately 79.99921% RTP after truncation; Rs.12.55 at 1.50x pays Rs.18.82 and has approximately 79.97875%. Values that cannot preserve integer paisa through the existing numeric wallet/API representation are rejected explicitly rather than silently dropping a paisa.

### Settlement, accounting and recovery

Winning gross payout is `stake * server-validated cashout multiplier` (rounded down to paisa); a loss pays zero. Player net P&L is payout minus stake. A transaction locks the round and wallet and commits the result and wallet credit together; a settled wager cannot pay twice. New wallet movements use integer paisa and append unique `stake`, `payout` or `refund` receipts to the existing SQL `multiplayerrequests` table, including wager identity, model, commitment, delta and before/after balances. Refund receipts survive cancellation even though the cancelled gameplay result is removed. Receipt insertion, wallet writes and result writes roll back together. Neither capped model enters the legacy daily pool, even when `DAILY_POOL_ENABLED=true`. Existing admin bet/payout reports read these same persisted outcomes. `GET /api/aviator/stats?table=aviator` (or `aviator-x`) returns combined v1/v2 settled stakes, payouts, GGR (`stakes - payouts`), player P&L and actual RTP (`payouts / stakes * 100`, null without settled stakes); clients see only their own totals, authenticated staff see the table aggregate. `modelsIncluded` identifies both included versions; nominal `theoreticalRtp: 80` and `theoreticalRtpAt199: 79.6` describe the current v2 rules, not a promised aggregate actual return. This endpoint paginates each model's results under the same game lock and sums integer paisa. Only `win`/`lose` outcomes enter settled RTP; pending, cancelled, refunded and invalid outcome statuses are excluded, while corrupt monetary values in a purported settled wager raise an explicit error. Negative GGR is valid and is never clamped.

Auto cashout is saved with the accepted wager and locked in the existing controls. The server settles at that exact saved target if it is strictly before the crash, including when a later read occurs after the crash or the browser disconnects. Processing is transactional/lazy, not a dedicated per-target timer: full game state/actions advance rounds, and the existing authenticated `POST /api/cron/daily-pools` scheduler also discovers pending new-model Aviator X players independently of pool entries. Run that existing scheduler regularly with `DAILY_POOL_CRON_SECRET` for abandoned-player recovery; without reads/scheduling the wallet credit is deferred until the next processing pass, not lost or recalculated at a later multiplier. The lightweight flight animation endpoint remains read-only. Cancelling an eligible waiting/queued wager refunds it without entering RTP totals.

New-model cashout thresholds and crash boundaries use `startsAt + ceil(log(multiplier)/growth * 1000)` on the SQL millisecond clock, including an immediate crash at takeoff for 1.00x. Manual requests use processing time after wallet and wager reads, not browser animation time or a client-supplied timestamp. If those reads cross a saved auto target, the saved automatic payout takes priority rather than paying a later manual multiplier. Requests without an eligible automatic cashout cannot pay at or after the authoritative crash boundary. Full-state and lightweight animation snapshots use the same boundary; a slow state read crossing it reports a crashed snapshot rather than a still-running flight. Already accepted legacy rounds keep their original clock and settlement contract.

### Commitment and verification

Each persisted round commits SHA256 of its UTF-8 hexadecimal server seed before accepting wagers, and commits the following round's seed for next-round reservations. New proofs also publish `nextVersion`; older proofs without it imply their own original version for the next commitment. During upgrade, the already-committed v1 successor is honored and publishes v2 for its following round, so already-accepted current/queued bets are never reinterpreted. Accepted wagers and movement receipts retain the model of their specific target round. State and bet receipts disclose hashes, versions, fixed public client seed and round-number nonce, never unrevealed seeds. New wagers also retain their accepted seed hash in the result. Before advancing/settling a model round, revealing a historical proof or publishing a lightweight snapshot, the server recomputes its crash using its original version and verifies the model, public client seed, nonce, current hash and next-seed commitment. Mismatches fail explicitly without wallet settlement; automatic targets and stored wager commitments are checked too. Once the round crashes, its seed is revealed in state/history and the existing rules panel. Verify the commitment and recompute the crash independently, using that round's published model:

```text
node scripts/verify-aviator-round.mjs aviator <round-number> <revealed-server-seed> <published-hash> <published-crash> <published-model>
node --test scripts/test-aviator-rtp.mjs
```

The verifier uses only Node crypto and an independent formula, checks commitment equality and any supplied published crash, and returns a failing exit code for a mismatch. Omitting the model preserves the original v1 CLI behavior; v2 proofs must explicitly supply `aviator-80-pre2-v2`. The test checks exact distribution boundaries for both versions at every supported cent target, the new strictly-below-2x probability and 1.99x RTP exception, paisa-rounded RTP for representative stakes at all targets, non-aliasing integer timing thresholds, and five million cryptographically sampled v2 outcomes with seven-standard-deviation binomial bounds (including the intended 1.00x/99.99x masses and raw sample bins). It also covers real HMAC rounds for both tables, gross payouts, automatic settlement, SQL-style rollback, replay protection, seed secrecy/reveal, commitment continuity and a real-proof v1-to-v2 transition with manual/automatic payouts, refunds and scheduler recovery. Finite samples fluctuate, especially at high targets.

The public client seed is fixed and **not player-contributed entropy**. Commitment/reveal proves consistency with a published seed, not that an operator did not preselect or discard seeds. Runtime validation detects inconsistent records, but cannot make the database immutable against an administrator who can replace all records and commitments; players should retain their original published hashes. HMAC output uniformity/independence relies on the standard cryptographic pseudorandomness assumption; empirical simulations do not prove a CSPRNG. Settlement concurrency/failure tests use the in-memory transactional harness and mocked SQL-connection tests, not live-money wagers or independent database certification. This implementation and its internal mathematical/simulation checks are **not independent fairness certification or regulatory approval**. Before real-money deployment, obtain applicable jurisdiction-specific licensing/compliance review and independent RNG, seed-lifecycle and game-math certification; retain auditable commitments/results. Do not treat passing tests as authorization to deploy real-money play.

Previously accepted legacy wagers retain their original payout contract and active legacy rounds finish without rewriting their saved crash; new wagers are refused on a pre-model round until the next model round. Therefore drain existing legacy rounds/reservations before a rollout advertised as universally sub-100x. No data migration deletes or rewrites accepted wagers. Skipped empty idle intervals have no wagers; the next actual round still uses the previously committed next seed.

## Authentication

Player-facing sessions include a permanent random seven-digit `displayId` (1000000-9999999), generated using Node's cryptographic random generator. The `player_display_ids` MySQL table stores it in the unique `random_id` column; collisions are retried, and repeat/concurrent requests reuse the saved value. On first use after upgrading, the application adds this column and assigns existing sequential-ID players a random ID once, without deleting their old mapping. The database user must have permission to alter this table. Internal user IDs, login credentials, referrals, and wallet relations are unchanged. The player menu, profile, and profile details provide an ID copy button with success/failure feedback (clipboard access requires HTTPS or localhost); the lobby account card does not display the ID. The profile displays this numeric ID, a fixed presentation-only `Credit Score: 100` (not a risk/scoring system), and a Pakistan flag beside the PKR balance capsule. Refresh failures keep the displayed balance and show an explicit error.

On first initialization, the configured `SUPER_ADMIN_*` values are used to create the super-admin account if it does not already exist. There are no guaranteed built-in demo client, agent, or sub-admin accounts.

## Deployment

### Hostinger (Node.js hosting)

Do not upload the raw project (without `node_modules`/`.next`) and rely on Hostinger to run `npm install` — its dynamic `mysql2` import is invisible to that flow and Hostinger will report the MySQL driver as missing. Instead, build a self-contained bundle locally and upload that:

```bash
npm install
npm run build
npm run package:hostinger
```

This produces a `deploy/` folder containing `server.js`, a pruned `node_modules` (with `mysql2` included), `.next/static`, and `public/`. Zip the **contents** of `deploy/` (not the project root) and upload/extract that on Hostinger. In hPanel's Node.js app settings:

- Startup file: `server.js`
- No `npm install` step needed — everything required is already inside `node_modules`
- Set the same `MYSQL_*`/`SUPER_ADMIN_*` environment variables in hPanel (or keep the `.env` file, which is already copied into `deploy/`)

Repeat `npm run build && npm run package:hostinger` and re-upload on every future deploy.
